Two measurements taken on 2026-08-22 against the host Ollama, using the real
`build_listing_prompt` output for a thin Vietnamese listing
(`"bat men xanh" / "gom Bat Trang, 15cm, vuot tay"`). Both change what this
week should prioritise.

### Finding 1 — the timeout is set below the cold-start cost

| Run | Wall | Model load |
|---|---|---|
| 1 (cold) | **21.4s** | 6.6s |
| 2 (warm) | 13.0s | 0.1s |
| 3 (warm) | 15.0s | 0.1s |

`OLLAMA_TIMEOUT_SECONDS` is 25. A cold start on an *idle* GPU already burns
21.4s of it. The first seller after any idle period is one contended GPU away
from a 503, and the client sends no `keep_alive`, so the model unloads and
every quiet hour re-pays the 6.6s load. This is not a tuning preference; it is
the difference between a feature that works and one that fails intermittently
for reasons no one can reproduce.

### Finding 2 — it gets Vietnamese ceramics terminology wrong, inconsistently

Same prompt, three runs at `temperature=0.4`:

| Run | `technique` | `material` |
|---|---|---|
| 1 | `hand-built` | `null` |
| 2 | `vuot tay` (untranslated) | `null` |
| 3 | `hand-built` | `Bat Trang` |

**`vuốt tay` means wheel-thrown, not hand-built.** They are different
techniques, and the peer-vocabulary block *offered* `wheel-thrown` — the model
declined it. So the optimizer will confidently write a false attribute onto a
seller's listing, and it will write a different one each time it is asked.

Nothing catches this. `find_blocked_claims` covers safety and commercial
claims only. `find_unsupported_claims` tokenises `hand-built` into
`hand`/`built`, neither of which is in `CLAIM_MARKERS`. The guardrails are
sound for what they were built for; this is a category they were not built for.

## The week

### Mon 24 — Unblock, then re-measure honestly

1. `sudo back_end/scripts/fix-ollama-host-binding.sh`, confirm
   `/api/v1/ai/health` flips `ollama` to `reachable` and `listing_optimizer`
   to `true`.
2. First end-to-end suggestion **through Traefik**, not against raw Ollama.
   Everything measured so far bypassed the service, the guardrails and the
   cache.
3. Add `keep_alive` to the `ollama_client` payload so the model stays resident
   between sellers. Re-measure cold and warm.
4. Re-set `OLLAMA_TIMEOUT_SECONDS` from the new numbers. Ceiling is Cloudflare's
   100s edge limit, and the client retries once, so the hard cap is 45.

**Done when:** a suggestion returns through the gateway in under 20s, twice in
a row, with the model resident.

### Tue 25 — Quality gate on the optimizer

The feature ships to sellers or it does not, and right now there is no number
to decide on.

1. Assemble ~20 real listings from the seed data — mixed Vietnamese and
   English, mixed completeness. Thin listings are the point; complete ones
   have nothing to optimise.
2. Score each run for: attribute accuracy (the `vuốt tay` class of error),
   guardrail firing, echo rate (rule 6 — proposals identical to input), and
   run-to-run stability on the same input.
3. Decide the fix for Finding 2. Three candidates, cheapest first:
   - a Vietnamese ceramics glossary block in the prompt (`vuốt tay` →
     wheel-thrown, `nặn tay` → hand-built, `men` → glaze, `gốm` → stoneware);
   - drop `temperature` toward 0 for attributes specifically — they are
     extraction, not writing, and the variance above is pure cost;
   - stop proposing `technique`/`material` outright and always route them to
     `ask_seller`, which the schema already supports.

**Done when:** an accuracy figure exists on paper and there is a written
go/no-go on exposing the button to real sellers. A no-go is a fine outcome —
an unmeasured yes is not.

### Wed 26 — Go public

1. **Decide the hostname first.** `api.mercai.tuan1970.com` is two labels deep
   and Cloudflare's free wildcard covers one, so the app will fail TLS as
   things stand. Flattening to `mercai-api.tuan1970.com` is free and is a
   one-line change in two files; Advanced Certificate Manager is ~$10/month.
   Everything downstream depends on this, so it is the first task of the day.
2. Work `DEPLOYMENT_CLOUDFLARE.md` end to end: create tunnel → install config →
   `ingress validate` → route DNS → run → verify.
3. Rotate the database password off the shared `Mysql_2025` default while the
   volume is still disposable. It gets expensive after there is real data.

**Done when:** the health check passes over HTTPS from a network that is not
this LAN.

### Thu 27 — Mobile end-to-end on the domain

1. Production build of the Expo app against the live hostname.
2. On a real device, on mobile data, not the emulator: log in, browse products,
   confirm images resolve from `/static/uploads`, open a chat (the WebSocket
   upgrade through the tunnel is the part most likely to break), and take one
   AI suggestion through accept-and-apply.
3. Video upload against Cloudflare's 100MB body cap — measure what the app
   actually produces. If real uploads exceed it, the feature needs
   direct-to-storage, and better to know now than from a seller.

**Done when:** one seller flow completes on a phone that has never been on this
network, AI suggestion included.

### Fri 28 — Pick the next increment

Three candidates, and the honest answer depends on Tuesday's number.

- **Chat copilot** (`docs/ai-features/03`) — designed, ranked #2, best-provisioned
  data in the schema. Reuses the whole `ai-service` foundation.
- **Review intelligence** (`docs/ai-features/04`) — designed, cheap to build, but
  worthless until review volume exists. Building it early means it switches
  itself on later.
- **Price intelligence** — decided in principle, not designed, and its own
  accuracy risk on real Vietnamese pages is still unvalidated. That validation
  (5–10 real URLs) is a half-day and should happen before any design work.

If Tuesday says the optimizer's grounding is weak, none of these should start:
the same weakness sits under all three, and fixing it once is worth more than
three features that each inherit it.

**Done when:** one choice is written down with its first task queued.

## Standing risks

- **GPU contention.** The stock project ships its own Ollama container behind a
  `gpu` profile. If it is ever started, two models compete for the 3060's 12GB,
  and the 184s/page anomaly from the price-intel benchmark is what that looks
  like. Anything timing-sensitive should check what is resident first.
- **The tunnel exposes everything Traefik routes.** The dashboard is on `:8080`
  with no ingress rule and should stay that way.
- **Ollama has no authentication** and is now bound to `0.0.0.0`. Firewall it if
  this host is ever on an untrusted network.

## Explicitly not this week

Anything from `PLAN_TODO_VERSION_2.md`'s 44 frontend/backend API mismatches.
None of them block the deploy, and starting there would trade a week of
measurable progress for a long tail of small fixes.
