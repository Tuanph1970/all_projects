# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Start here every session

Before doing anything else, open **`ROADMAP.xlsx`** at the repo root. It is the source of truth for project status:

- **Sessions Log** sheet — read the last row's "Where I left off" to know what was in flight.
- **Feature Inventory** — every feature with current Status (Done / In Progress / Partial / Stub / Planned / Not Started). Filter on Status to see what's open.
- **Backlog** — concrete TODOs with `file:line` references; pick from here when starting a session.
- **Roadmap** — phased plan (Phase 2 build → Phase 3 migration → Phase 4 polish → Phase 5 growth).
- **Tech Debt**, **Architecture** — orientation references.

After making changes, update the matching Status cell(s) in **Feature Inventory** / **Backlog** / **Roadmap**, and append a row to **Sessions Log** with what you did and where you left off. The user works in long gaps between sessions — keeping this workbook current is how they regain context.

The workbook is regenerated by `build_roadmap_excel.py` (repo root). Edit the data lists in that script for structural changes; for routine status updates, edit the workbook directly.

## Repository layout

This repo is a polyglot monorepo for a Vietnamese stock-market platform. Three top-level units that you will touch most:

- `stock_microservices/` — Python (FastAPI) microservices behind a Traefik gateway, plus shared `stock-common` library, RabbitMQ, Redis, and observability stack.
- `stock_react_javascript/stock-react-app/` — Create-React-App frontend (React 19) consuming the gateway.
- `deploy.sh` + `docker-compose.full-stack.yml` (repo root) — full-stack orchestration that wires the React app, the microservices stack, MySQL, and monitoring together.

`PHASE2_IMPLEMENTATION_PLAN.md`, `PHASE3_IMPLEMENTATION_PLAN.md`, and `WORK_IN_PROGRESS.md` (inside `stock_microservices/`) capture the migration story from a prior Django monolith. Read them when a task touches migration scripts, cutover, or "WebAPI-compatible" tables — they explain why some tables/seed data live alongside SQLAlchemy models.

## Architecture (big picture)

### API gateway and service routing
All HTTP traffic enters via **Traefik** on port `8004` (full-stack) or repo-internal `8004`. Traefik routes by `PathPrefix(/stock_helper/api/v2/<area>)` to the matching service. The mapping is defined by Docker labels in `stock_microservices/docker-compose.yml`:

| Path prefix | Service | Internal port |
|---|---|---|
| `/auth` | auth-service | 8007 |
| `/companies`, `/stocks`, `/market`, `/industries`, `/priceboards` | stock-data-service | 8001 |
| `/portfolio` | portfolio-service | 8003 |
| `/predictions`, `/predict`, `/models`, `/solutions` | prediction-service | 8002 |
| `/analysis` | analysis-service | 8004 (internal) |
| `/ai` | ai-insights-service | 8005 |
| `/chat` | chatbot-service | 8006 |
| `/journal` | journal-service | 8008 |
| `/knowledge-qa` | knowledge-qa-service | 8009 |
| `/helper` | decision-helper-service | 8010 |

The frontend reaches all of these through `REACT_APP_API_URL` (defaults to `http://localhost:8004`) — see `stock_react_javascript/stock-react-app/src/constants/api.js` for the canonical endpoint table; do not hardcode service URLs in components.

### Service shape (FastAPI)
Each service under `stock_microservices/services/<name>/` follows the same internal layout:

```
app/
  main.py            # FastAPI app, lifespan, /health/{live,ready}, /metrics
  config.py          # pydantic-settings; reads env vars
  api/routes.py      # HTTP endpoints; mounted under API_PREFIX
  models/            # SQLAlchemy domain + pydantic schemas
  repositories/      # DB access
  services/          # business logic
```

The lifespan in `main.py` typically (a) creates SQLAlchemy tables, (b) ensures legacy "WebAPI-compatible" tables, (c) applies idempotent ALTER migrations, (d) seeds reference data with `INSERT IGNORE`. `prediction-service/app/main.py` is the most extensive example — it carries the full model-management schema (`tbl_solution`, `tbl_model_field`, `technical_indicators`, etc.) and seed data inline. When changing those schemas, update the inline SQL **and** any matching SQLAlchemy `Base` definitions.

### Shared library: `stock-common`
`stock_microservices/stock-common/stock_common/` is a local package (`pip install -e`) that every service depends on. Use it instead of reinventing:

- `auth/` — JWT issuing/parsing, password hashing, FastAPI auth middleware. Auth-service is the issuer; other services validate via this lib.
- `database/` — async SQLAlchemy connection helpers and a generic repository base.
- `events/` — `EventBus` (aio-pika), `Event`/`EventMetadata` models, and `@event_handler` decorator for RabbitMQ-based async messaging.
- `observability/` — structured logging (structlog), Prometheus metrics, OpenTelemetry/Jaeger tracing helpers.
- `resilience/` — circuit breaker and retry (tenacity).
- `config.py` — common pydantic-settings base.

Service Dockerfiles `COPY stock-common /app/stock-common && pip install -e /app/stock-common` — local edits to the lib propagate on next image build.

### Data and infra
- **MySQL** is the system of record. Locally services connect to `host.docker.internal:3306` (a host-side MySQL or the SSH-tunnel container that forwards to a remote DB). The `mysql` service in compose is gated behind the `local-db` profile and is for fallback only.
- **Redis** is shared cache (`stock_redis`, internal only).
- **RabbitMQ** is the event bus (`/stock` vhost, `stockuser`/`stockpass` defaults).
- **Observability**: Prometheus scrapes `/metrics` on each service; Grafana dashboards live in `monitoring/grafana/provisioning`; Jaeger receives OTLP from the `TRACING_*` env vars wired into every service.
- **Ollama + Neo4j** power the `knowledge-qa-service` (Graph RAG). Ollama runs under `--profile gpu` (default: `ollama-gpu` with NVIDIA) or `--profile cpu`; Neo4j is expected on the host at `bolt://host.docker.internal:7687`.

### Migrations and cutover
`stock_microservices/migrations/` holds the Django→microservices data migration tooling: `run_migration.py` is the master orchestrator with `--mode dry_run|initial|verify`; per-table scripts live under `migrations/scripts/`; `migrations/sync/sync_service.py` runs continuous sync during shadow mode; `migrations/rollback/` has emergency rollback. `stock_microservices/cutover/cutover.py` plus `stock_microservices/feature-flags/` drive the staged switchover.

## Common commands

### Full-stack (repo root)
```bash
./deploy.sh                 # bring up frontend + microservices + monitoring
./deploy.sh --build         # rebuild images first
./deploy.sh --status        # docker compose ps
./deploy.sh --logs <svc>    # follow logs for one service
./deploy.sh --stop          # stop everything
./deploy.sh --clean         # stop + drop volumes (prompts)
```
Frontend lands at `http://localhost:3004`, gateway at `http://localhost:8004`, Grafana at `http://localhost:3100`.

### Microservices stack only
```bash
cd stock_microservices
docker compose up -d                          # core services + Traefik + RabbitMQ + Redis + monitoring
docker compose --profile gpu up -d ollama-gpu # add GPU-backed LLM (or --profile cpu)
docker compose --profile local-db up -d mysql # local MySQL fallback
docker compose --profile remote-db up -d ssh-tunnel  # tunnel to remote MySQL
./scripts/deploy.sh --health                  # health-check sweep
./scripts/deploy.sh --test                    # exercise public endpoints
```

### Tests (Python)
Pytest config in `stock_microservices/pytest.ini` (`asyncio_mode=auto`, custom markers: `integration`, `e2e`, `performance`, `security`, `slow`, `auth`, `database`).
```bash
cd stock_microservices
./scripts/run-tests.sh --integration          # default; expects services up locally
./scripts/run-tests.sh --e2e
./scripts/run-tests.sh --performance
./scripts/run-tests.sh --all --coverage       # writes reports/coverage and reports/junit.xml
./scripts/run-tests.sh --docker --all         # spin up docker-compose.test.yml and run inside
./scripts/quick-test.sh                       # `-m "not slow" --timeout=10 -x`, fast feedback
./scripts/test-service.sh <auth|stock-data|portfolio|prediction|analysis|cross>  # single integration file
pytest tests/integration/test_auth_flow.py::test_login -v   # single test
pytest services/auth-service/tests -v         # per-service unit tests (run from repo root with PYTHONPATH or inside container)
```
`run-tests.sh --local` first hits each service's `/health/live`; if any are down it aborts with the docker-compose hint — start the stack before re-running.

### Frontend
```bash
cd stock_react_javascript/stock-react-app
npm install
npm start          # dev server on :3000 (homepage is /stock-app)
npm test           # interactive react-scripts test
npm test -- --watchAll=false MyComponent.test  # one file, no watch
npm run build      # production bundle into build/
```
The dev server expects the gateway on `http://localhost:8004`; override with `REACT_APP_API_URL` if running against a non-default host.

### Migrations
```bash
cd stock_microservices/migrations
pip install -r requirements.txt
python run_migration.py --mode dry_run        # always run first
python run_migration.py --mode initial --confirm
python run_migration.py --verify-only
```

## Conventions worth knowing

- **API prefix** is `/stock_helper/api/v2/<area>` end-to-end. Don't change the prefix on one side without updating Traefik labels and `src/constants/api.js`.
- **Service names** use kebab-case (`auth-service`); env vars use SCREAMING_SNAKE; React paths use camelCase. Keep the existing pattern when wiring a new service into compose, gateway labels, and `API_BASE_URLS`.
- **Health endpoints** are `/health`, `/health/live`, `/health/ready` on every service — the docker-compose healthchecks and `run-tests.sh` rely on `/health/live` being unauthenticated.
- **DB schemas live in two places** for `prediction-service`: SQLAlchemy `Base` (declarative models in `app/models/domain.py`) and the inline `WEBAPI_TABLES_SQL`/`MIGRATION_SQL`/`SEED_DATA_SQL` blocks in `app/main.py` for legacy WebAPI compatibility. Keep both in sync.
- **Frontend services** (`src/services/*.js`) wrap `httpClient.js` and pull URLs from `constants/api.js`. New backend endpoints get a constant added to `API_ENDPOINTS` and a method on the matching service class — components should not call `axios` directly (see `RESTRUCTURE_GUIDE.md`).
- **Auth flow**: `auth-service` mints JWTs with `JWT_SECRET_KEY`; every other service shares the same secret via env and validates locally using `stock_common.auth`. Don't introduce per-service secrets.

# CLAUDE.md — Standing Rules for the Chart Decomposition & Pattern Detection Work

These rules apply to **every** session that touches the chart decomposition / pattern
detection system. They are derived from `docs/SRS_master_chart_system.md`. Read that
spec before acting; this file is the short version of its binding constraints.

## The spec is the source of truth
- The full specification lives in `docs/SRS_master_chart_system.md`. Re-read the
  relevant Part/section before implementing anything; grep it rather than relying on
  memory of it.
- Requirement IDs (e.g. `FR-DECOMP-MODWT`, `FR-HURST`, `FR-PAT-HS`, `C1`–`C5`) are the
  canonical way to refer to features. Cite them in commits, tests, and docstrings.

## Fit the existing project — do NOT impose the spec's API verbatim
- The interfaces in the SRS (§I.4, §II.4) are explicitly **illustrative**. Match the
  existing codebase's module layout, naming, typing, error-handling, and dependency
  conventions instead of copying the spec's signatures literally.
- Before writing a module, check whether equivalent functionality already exists
  (see `docs/srs_gap_analysis.md`). Reuse and extend; never duplicate.

## Binding constraints (these override convenience)
1. **Strict causality (C1).** Any forecasting/feature code uses only data available at
   the prediction time. Never decompose a full series and then slice it into past/future.
   Feature builders take `(data_up_to_t)`, not a precomputed full-series matrix.
2. **No-leakage test is mandatory (§I.5.3).** Any forecasting path ships with the test
   that swaps past target values for noise and asserts past predictions do not change.
3. **Mode-ordering stability (C3).** Data-adaptive decompositions (EMD/EEMD/VMD) must be
   sorted by a stable key (center frequency for VMD, dominant period for EMD) before any
   feature is read across multiple refits.
4. **Mandatory benchmarks (C4).** Volatility models are always reported beside HAR;
   direction models beside lag-returns; pattern detectors beside a random-walk null-FPR.
   A method "improves" only if it beats the benchmark out-of-sample with significance.
5. **Boundary handling (C2).** Time-frequency outputs expose the cone of influence; live
   feature reads back off from the right edge (`edge_lag`).
6. **Stationary input for Hurst (FR-HURST).** Estimate Hurst on returns, never on price.

## Numbers from the spec are illustrative, not expected values
- All magnitudes in Part III (AUC ≈ 0.97, R² ≈ 0.89, etc.) come from synthetic data.
  Do NOT hardcode them as test assertions. Tests assert *properties* (e.g. "fGn Hurst
  recovered within 0.07", "no-leakage swap changes nothing", "VMD-HAR within ±10% of
  HAR") not specific simulator numbers.

## Workflow discipline
- One phase per session: design → plan → implement → document. Each phase writes a
  `docs/*.md` artifact that is the handoff to the next.
- During implementation, do ONE task from `docs/implementation_plan.md` at a time. Write
  its tests (TDD where practical: failing test first), run them, show they pass, then
  STOP. Do not start the next task without being asked.
- Prefer small, reviewable changes. Show diffs and test output.

## Testing
- Test runner: `pytest`. Every new module ships with unit tests.
- Mandatory harnesses, built alongside the code they validate (not after):
  round-trip reconstruction, translation-invariance (MODWT), fGn-Hurst recovery,
  wavelet-coherence on a known-construction pair, the no-leakage causality test, the
  planted-pattern test, and the null-FPR test.
